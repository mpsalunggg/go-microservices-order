    Konsep dasar

    Monolith vs microservices

    Monolith: semua fitur dalam satu aplikasi dan satu proses. Microservices: setiap fitur jadi aplikasi kecil sendiri yang berbicara lewat network.

    Analogi: monolith seperti satu restoran dengan satu dapur besar. Kalau kompor meledak, seluruh restoran tutup. Microservices seperti food court: tiap kios punya dapur sendiri. Satu kios tutup, kios lain tetap jualan.

    Fase 1 · Aturan emas

    Database per service

    Setiap service punya database sendiri. Service lain tidak boleh membaca tabelnya langsung, hanya lewat API atau event.

    user
    │
    user-dbtabel users · localhost:5433
    order
    │
    order-dbtabel orders · localhost:5434

    Di project ini terlihat di docker-compose.yaml: ada user-db dan order-db, dua Postgres terpisah. Migration juga terpisah: services/user/migrations dan services/order/migrations.

    Pertanyaan: kenapa orders.user_id bukan FOREIGN KEY ke users.id?

    Karena tabel users ada di database lain. Postgres tidak bisa membuat foreign key lintas database. Integritasnya dijaga oleh logika aplikasi: sebelum insert, order bertanya ke service user lewat HTTP (UserClient.Exists).

    Pertanyaan: kenapa tidak satu database bersama saja?

    Kalau order membaca tabel users langsung, tim user tidak bisa lagi mengubah skema tabelnya tanpa merusak order. Service jadi terikat erat lagi (distributed monolith): repotnya microservices, tanpa manfaatnya.

    Fase 2

    Komunikasi sync: HTTP dan timeout

    Sync berarti service A memanggil service B lalu menunggu jawabannya, seperti menelepon.

    Saat POST /orders, service order memanggil GET /users/{id} di service user. Di monolith panggilan ini hampir pasti berhasil. Lewat network, panggilannya bisa lambat, gagal, atau tidak pernah dijawab.

    Simulasi: order memanggil user
    0 dtk246+

    Apa yang dipelajari

    • Timeout: batas waktu menunggu. Tanpa timeout, satu service lambat membuat semua pemanggilnya ikut menggantung. Request menumpuk, memori habis, lalu service pemanggil ikut tumbang. Ini disebut cascading failure.
    • 503, bukan 500: kalau dependency bermasalah, order membalas 503 (service tidak tersedia sementara). 500 berarti bug di service itu sendiri.
    • 422 kalau user memang tidak ada: request valid secara format, tapi datanya tidak bisa diproses.
    • context membawa batas waktu dari request masuk ke semua panggilan turunannya. Kalau client batal, panggilan ke user ikut berhenti.
    // services/order/internal/userclient.go
ctx, cancel := context.WithTimeout(ctx, 2*time.Second)
defer cancel()
req, _ := http.NewRequestWithContext(ctx, http.MethodGet, url, nil)
    Retry (Langkah 5): hanya untuk error sementara (network, 502/503/504), maksimal 2–3 kali dengan backoff + jitter, dan hanya untuk operasi idempotent seperti GET. Retry yang sembarangan memperparah beban saat service sedang sakit (retry storm).
    Fase 3 · Kenapa butuh Kafka

    Sync vs async

    Sync seperti menelepon: harus menunggu diangkat. Async seperti kirim chat: pesan terkirim, kamu lanjut kerja, penerima membaca saat sempat.

    Misalnya setelah order dibuat, kita mau kirim notifikasi. Bandingkan dua cara: order memanggil notification langsung lewat HTTP, atau order menulis event ke Kafka dan notification membacanya sendiri.

    Simulasi: notification sedang mati

    order

    Kafka (antrean)

    hidup

    Coba: matikan notification, buat 3 order, lalu hidupkan lagi. Ulangi dengan mode Sync.

    Sync (HTTP)Async (Kafka)
    Kapan dipakaiButuh jawaban sekarang ("user ada?")Memberi tahu sesuatu sudah terjadi ("order dibuat")
    CouplingPemanggil harus tahu alamat penerima dan menungguProducer tidak tahu siapa consumer-nya
    Penerima matiRequest gagalPesan menunggu di Kafka, diproses saat penerima hidup
    Itulah alasan validasi user tetap sync (order butuh jawabannya sebelum menyimpan), sedangkan notifikasi async (order tidak perlu menunggu email terkirim).
    Fase 3 · Langkah 1–4

    Kafka: topic, partition, offset, key

    Kafka adalah log yang hanya bisa ditambah. Pesan tidak dihapus setelah dibaca. Pesan disimpan sesuai retention (default 7 hari), jadi bisa dibaca ulang.

    • Topic: kategori pesan, misalnya order.created.
    • Partition: topic dipecah supaya bisa dibaca paralel. Di project ini order.created punya 3 partition (lihat kafka-init di compose).
    • Offset: nomor urut pesan dalam satu partition: 0, 1, 2, dan seterusnya.
    • Key: menentukan partition. Key sama, partition sama. Urutan hanya dijamin di dalam satu partition.
    Simulasi: producer menulis ke topic order.created

    Catatan: simulasi ini memakai hash sederhana. Kafka asli memakai hash murmur2, tapi prinsipnya sama: partition = hash(key) % jumlah_partition.

    Kode producer di project ini, services/order/internal/publisher.go:

    record := &kgo.Record{
	Topic: TopicOrderCreated,                          // "order.created"
	Key:   []byte(strconv.FormatInt(evt.OrderID, 10)), // key = order_id
	Value: value,                                      // JSON OrderCreated
}
return p.client.ProduceSync(ctx, record).FirstErr()

    Kontrak event

    Event adalah fakta yang sudah terjadi, jadi namanya past tense: OrderCreated. Event adalah kontrak publik: field boleh ditambah, tapi jangan dihapus atau diganti nama, karena consumer bergantung padanya.

    {"event_id":"K7Q2...","order_id":12,"user_id":7,"amount":50000,"created_at":"2026-10-26T10:00:00Z"}

    Fase 3 · Langkah 5

    Consumer group

    Consumer group adalah sekelompok instance dari service yang sama. Kafka membagi partition ke anggota group, jadi setiap pesan diproses satu anggota saja.

    Simulasi: scale service notification
    • 1 instance: semua 3 partition dibaca satu instance.
    • 3 instance: tiap instance dapat 1 partition, kerja paralel.
    • 4 instance: satu menganggur. Jumlah consumer aktif dalam satu group maksimal sama dengan jumlah partition.
    • Group berbeda (notification dan analytics) masing-masing mendapat salinan semua pesan, dengan offset masing-masing.

    Di project, coba langsung:

    docker compose up -d --scale notification=3
make kafka-lag
    Fase 3 · Langkah 5–6

    Commit offset, at-least-once, idempotency

    Consumer mencatat (commit) offset terakhir yang sudah diproses, seperti pembatas buku. Di project ini commit dilakukan setelah pesan diproses.

    kgo.DisableAutoCommit()            // commit manual
...
for _, record := range fetches.Records() { handle(record) }
client.CommitUncommittedOffsets(ctx) // "sudah selesai sampai sini"

    Akibatnya: kalau service mati setelah memproses tapi sebelum commit, pesan dibaca ulang setelah restart. Tidak ada pesan hilang, tapi bisa terproses dua kali. Ini disebut at-least-once.

    Simulasi: crash sebelum commit

    Garis hijau bawah = offset ter-commit · garis putus oranye = posisi baca berikutnya

    NOTIFIKASI TERKIRIM KE USER

    Skenario: Poll → Proses → Crash → Poll → Proses. Lihat notifikasi dobel. Lalu Reset, nyalakan idempotency, dan ulangi.

    Idempotency

    Idempotent berarti memproses pesan yang sama dua kali hasilnya sama dengan sekali. Caranya: catat event_id yang sudah diproses di database.

    tag, err := db.Exec(ctx,
	`INSERT INTO processed_events (event_id) VALUES ($1) ON CONFLICT DO NOTHING`,
	evt.EventID)
if tag.RowsAffected() == 0 {
	return nil // sudah pernah diproses, lewati
}
// ... kirim notifikasi
    Ini Langkah 6 berikutnya di roadmap: tambah notification-db dan tabel processed_events.
    Fase 3 · Langkah 5

    Dead letter queue: order.created vs order.created.dlq

    order.created adalah jalur normal. order.created.dlq adalah "tempat sampah" untuk pesan yang gagal diproses, supaya tidak memblokir pesan lain.

    Simulasi: ada pesan rusak (not-json)
    order.created
    ….dlq

    Tanpa DLQ hanya ada dua pilihan buruk:

    1. Retry terus: pesan rusak tetap rusak. Consumer macet dan semua pesan di belakangnya tertahan (poison message). Matikan "pakai DLQ" di simulasi untuk melihatnya.
    2. Dibuang: data hilang, tidak bisa diselidiki.

    Kode di services/notification/cmd/main.go:

    if err := handle(log, record); err != nil {
	dlq := &kgo.Record{Topic: topicDLQ, Key: record.Key, Value: record.Value}
	if err := client.ProduceSync(ctx, dlq).FirstErr(); err != nil {
		return fmt.Errorf("produce to DLQ: %w", err) // berhenti tanpa commit
	}
}

    Coba di project:

    docker compose exec -T kafka /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server kafka:29092 --topic order.created \
  --property parse.key=true --property key.separator=: <<< '43:not-json'

docker compose exec kafka /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server kafka:29092 --topic order.created.dlq --from-beginning --property print.key=true
    Fase 3 · Langkah 4 → 7

    Masalah dual write dan outbox pattern

    Handler order sekarang menulis ke dua sistem: Postgres lalu Kafka. Tidak ada transaksi yang mencakup keduanya.

    INSERT order ✅  →  Publish Kafka ❌  = order ada, event hilang
Publish Kafka ✅ →  INSERT order ❌   = event ada, order tidak ada

    Outbox: tulis event ke tabel outbox di database yang sama, dalam satu transaksi dengan insert order. Worker terpisah membaca outbox setiap detik lalu mengirimnya ke Kafka.

    Simulasi: Kafka mati atau service crash

    order-db: orders

    order-db: outbox

    Kafka: order.created

    Outbox juga at-least-once: kalau Kafka sudah menerima pesan tapi UPDATE published_at gagal, pesan dikirim ulang. Karena itu consumer wajib idempotent (langkah sebelumnya).
    ┌──────── 1 transaksi ────────┐
│ INSERT INTO orders ...      │
│ INSERT INTO outbox ...      │
└─────────────────────────────┘
           │
   Outbox worker (tiap 1 detik, FOR UPDATE SKIP LOCKED)
           ▼
         Kafka  →  UPDATE outbox SET published_at = now()
